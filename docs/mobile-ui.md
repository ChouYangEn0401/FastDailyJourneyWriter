# 手機版介面

同一份 `web/`，在手機上換一種排法。這份文件記錄**為什麼這樣排**，
以及過程中撞到的幾個坑。

> **狀態：版面在無頭 Chrome 的 390 / 320 / 768 / 1440 四種寬度看過，**
> **但還沒有在任何一支真的手機上開過。** 待驗清單在最後。

---

## 一、原本的問題

桌機版是三欄：左邊選題組、中間寫、右邊輸出。

820px 以下三欄疊成一欄，順序照 HTML 的順序來，於是變成：

```
題組（19 個，分五群）      ← 大約一個半螢幕
版型（4 個）
紙張顏色（5 個）
最近的日記
編輯區                      ← 你打開 app 想做的事，在這裡
輸出（3 塊）
```

**要寫一行字，得先滑過四個面板的設定。** 這不是「有點擠」，
是把最常做的事放在最難到達的地方。

---

## 二、四個畫面

底部一條分頁列，一次只顯示一個畫面：

| 分頁 | 裡面有什麼 | 什麼時候用 |
|---|---|---|
| **✎ 寫** | 日期、標題、換色列、題目、給主的話 | **預設**。打開就在這裡 |
| **❖ 題組** | 題組、版型、紙張顏色 | 偶爾換一次 |
| **▤ 輸出** | 頁面、卡片、畫圖 prompt、記住設定 | 寫完才用 |
| **☰ 日記** | 最近的日記、備份與垃圾桶 | 想翻回某一天 |

分法的判準是**使用頻率**，不是原本在畫面的哪一邊。
「最近的日記」在桌機版屬於左欄，但它跟「換題組」是兩件完全不同的事，
所以在手機上分開。

### 選完就回去寫

點題組、點某一天的日記、按「＋ 新的一天」——這三個動作做完會**自動跳回「寫」**。

它們都是「為了開始寫」才做的，停在清單上等你再按一次分頁列，
等於每次都要多按一下。換版型和換顏色**不會**跳回去，
因為那通常要連續試好幾個。

### 打字的時候分頁列會收起來

鍵盤已經吃掉半個螢幕，分頁列再吃 56px 就太多了，
而且**打到一半也不會想切換畫面**。

游標進到任何輸入框就收起來，離開就回來
（`web/app.js` 的 `syncTypingState`）。
`focusout` 那邊延遲一個 tick 才判斷——不然從一題跳到下一題時，
分頁列會閃一下。

## 三、為什麼是分頁列，不是漢堡選單

漢堡選單把東西藏在一個要按兩次才看得到的地方。
這個 app 只有四塊，四塊都值得一直看得到——
**看得到「輸出」這件事本身就在告訴人：你寫的東西可以變成別的形狀。**

分頁列也一直在拇指構得到的位置。頂部的選單不是。

沒有用 `role="tablist"`：那組 ARIA 角色有一整套鍵盤操作與
`aria-controls` 的約定，這裡沒有實作。宣告一個做不到的角色，
對讀螢幕的人來說比什麼都不說更糟。就是四個按鈕，加 `aria-current="page"`。

---

## 四、怎麼做到的

**一個中斷點：820px。** 跟原本三欄塌成一欄的中斷點同一個。
兩個中斷點就會有兩套要對的心智模型。

**沒有搬動任何 DOM。** 每個區塊掛一個 `data-m-tab`，說自己屬於哪個畫面：

```html
<section class="panel" data-m-tab="setup">
<section class="editor" data-m-tab="write">
```

CSS 只在 820px 以下理它：

```css
[data-m-tab]{display:none;}
body[data-view="setup"] [data-m-tab~="setup"]{display:block;}
```

820px 以上這些屬性完全沒作用，**三欄版面一行都沒改**。

被藏起來的面板還在 DOM 裡，所以 `buildForm()`、`collect()`、
自動存檔讀的都還是同一批節點——切分頁不會弄丟正在打的字。

**`.rail{display:contents}`**：兩條側欄在手機上不再是盒子，
讓裡面的面板直接變成 `.layout` 的子項。
不然一條面板全被藏起來的側欄，還是會留下一格 `gap`。

## 五、踩到的坑

記在這裡，因為每一個都會再遇到。

**`align-items:start` 讓編輯區長得比螢幕寬。**
三欄版面用的是 `align-items:start`。改成 flex 直排之後，
這個值的意思變成「每個面板照自己的內容決定寬度」，
而編輯區的內容比手機寬——整頁就多了一條橫向捲軸。
手機那段要明確寫回 `align-items:stretch`。

> 抓法：把每個元素的 `getBoundingClientRect().right` 跟
> `documentElement.clientWidth` 比一比。多出來的那個就是兇手。

**iOS 會在你點小於 16px 的輸入框時放大整頁。**
內文是 15px，輸入框繼承下去就是 15px，於是**每點一題畫面就縮放一次**，
而且不會自己縮回來。手機那段把所有輸入元素（含 `contenteditable`）
釘在 16px。

**標題那一列在小螢幕會擠成直的。**
320px 寬時「AI 取名」被壓到一個字一行。
標題欄改成 `flex:1 1 100%`，永遠自己佔一整行。

**捲軸套捲軸。** 「最近的日記」原本是 `max-height:320px` 的小捲動框。
在自己的畫面上不需要——拿掉，讓整頁捲。

**對話框改成從底部升起。** 置中的對話框會被鍵盤推來推去，
關閉鈕跑到難以預測的位置。貼著下緣就不會。

**安全區域。** `viewport-fit=cover` ＋ `env(safe-area-inset-*)`，
分頁列才不會被瀏海機的 home indicator 蓋住。

**用 `dvh` 不用 `vh`。** 手機瀏覽器的網址列會收合，`100vh` 因此會算錯。

**觸控目標。** 編輯題組的鉛筆本來是 30px 寬，色票 22px。
手機上分別放大到 46px 和 32px，分頁列每個按鈕至少 48px 高。

## 六、驗過什麼、沒驗過什麼

**驗過的**（無頭 Chrome 開 DevTools protocol，390 / 320 / 768 / 1440）：

- 四個畫面各自只顯示自己的內容
- 沒有橫向溢出（`scrollWidth == clientWidth`）
- 桌機三欄版面沒有變化
- 打字時分頁列收起、提示訊息跟著讓位
- 對話框以底部面板呈現

- 主控台沒有任何錯誤或警告，也沒有請求失敗

**沒驗過的**：

- [ ] **任何一支真的手機。** 這是最大的一項
- [ ] service worker 有沒有真的裝起來——無頭 Chrome 不讓它進入 active
      狀態，細節見 [platforms/pwa/](../platforms/pwa/README.md)
- [ ] iOS Safari。安全區域、`dvh`、鍵盤行為都是 Safari 最容易不一樣的地方
- [ ] 真的用手指點。上面的尺寸是照 44px 的通則調的，不是量出來的
- [ ] 橫向持握
- [ ] 深色模式在手機上的樣子
- [ ] 讀螢幕軟體（VoiceOver / TalkBack）
- [ ] 卡片的 PNG 下載。iOS Safari 對 `a[download]` 的處理跟其他瀏覽器不同，
      很可能是直接開新分頁而不是存檔
