# 接下來的方向

這份文件記錄**還沒做的決定**和決定背後的理由，特別是「手機版要怎麼走」。
單純的功能點子在 [IDEAS.md](../IDEAS.md)。

## 先講結論

| 問題 | 結論 |
|---|---|
| 要不要按作業系統分資料夾（windows/mac）？ | **不要。** 同一份 Python 在兩邊跑，分了只會有兩份會走鐘的副本 |
| 手機版要不要開新專案？ | **不要。** 同一個 repo，多一層資料夾就好 |
| 手機版難在哪？ | 難的不是打包，是**後端是 Python**。Python 上不了 App Store |
| 那要做什麼？ | 把 `backend/render/` 的輸出核心搬到 JavaScript。**這件事做完，手機版剩下的都是雜事** |

## 一、為什麼不按作業系統分資料夾

整個 `backend/` 裡面沒有任何一行跟作業系統有關的程式碼（沒有 `sys.platform`、
沒有 `os.name`、沒有寫死的路徑分隔符號）。Python 本來就是跨平台的，
路徑一律走 `pathlib`。

**同一份程式碼在 Windows、macOS、Linux 上跑出來的結果完全一樣。**

真正跟平台有關的東西只有「怎麼按下去啟動」，而那已經處理掉了：

```
run.bat    Windows        →  .venv\Scripts\python.exe run.py
run.sh     macOS / Linux  →  .venv/bin/python run.py
```

兩個檔案加起來不到 10 行。為了這 10 行去分 `windows/` 和 `mac/` 兩個資料夾，
代價是**同樣的 31 個 Python 檔要維護兩份**——改一個 bug 要改兩個地方，
遲早會忘記其中一邊。這是很常見的錯誤直覺，值得明確擋下來。

> **判準**：資料夾要按「**這段程式碼會不會不一樣**」來分，
> 不是按「**它會在哪台電腦上跑**」來分。

## 二、手機版真正的難處

打包不是問題。問題是**這個程式的一半是 Python，而 Python 上不了手機**。

現在的分工：

| 層 | 用什麼寫 | 能不能直接上手機 |
|---|---|---|
| `content/` 題組與版型 | JSON + Jinja2 | ✅ 可以，本來就是純資料 |
| `web/` 介面 | 原生 JS | ✅ 可以 |
| `backend/render/` 輸出 HTML 與卡片 | **Python** | ❌ 不行 |
| `backend/storage.py` 存檔 | **Python + SQLite** | ❌ 不行 |

（技術上有 Kivy、BeeWare、Chaquopy 這類方案可以把 Python 塞進手機，
但體積大、啟動慢，而且 App Store 的審查對這種做法一向不友善。不建議。）

所以手機版不是一個「打包工作」，是一次**移植**。要移植的具體有這些：

| 檔案 | 難度 | 備註 |
|---|---|---|
| `render/document.py` | 低 | 純資料轉換，照抄邏輯就好 |
| `render/artifact_html.py` | 低 | Jinja2 → **Nunjucks**，語法幾乎一樣，`content/layouts/*.j2` 可以原封不動沿用 |
| `render/themes.py` | 低 | 五組顏色常數 |
| `richtext.py` | 中 | HTML 白名單清理、色彩 run 解析 |
| `storage.py` / `backup.py` | 中 | SQLite → Capacitor SQLite 或 IndexedDB。**歷史版本、垃圾桶那套邏輯要一起搬** |
| `render/card_svg.py` + `textlayout.py` | **高** | 手算 SVG 排版 + 中英混排斷行（含避頭尾）。最花時間的一塊 |

> **`content/` 已經先搬出後端了**（本來在 `app/seed/`）。
> 那一層沒有一行 Python，將來任何客戶端都可以直接沿用同一批檔案——
> 題目怎麼問、版面長什麼樣，是這個工具最有價值的部分，不該綁在後端上。

### 卡片那一塊可以偷懶

`card_svg.py` 是最難移植的，但手機上其實不用重寫：
**卡片可以先產生 HTML，再讓瀏覽器/WebView 自己畫成圖**
（`html2canvas`，或直接用現成的 HTML→圖片）。
排版交給 CSS，就不用再實作一次斷行演算法。值得先試這條路。

## 三、三條路線

### 路線 A — PWA（先做這個）

把移植好的 JS 核心配上 service worker，使用者用瀏覽器開，按「加到主畫面」。

- **成本**：只有上面那張移植表。不用 Mac、不用 Xcode、不用 Android Studio
- **好處**：iPhone 和 Android 同時搞定；不用審查、不用上架費、不用被抽成；改版即時生效
- **代價**：App Store / Google Play 搜不到（沒有商店曝光）；
  iOS 的 PWA 在長期不用時**有被系統清掉儲存空間的風險**——
  對日記 app 來說這件事要特別小心，一定要配合「匯出全部」提醒使用者備份

### 路線 B — Capacitor 包成原生 app（A 做完再做）

[Capacitor](https://capacitorjs.com/) 把 A 的網頁包成真的 app。

- **前提**：**A 必須先做完。**B 沒有 A 就沒有東西可以包
- **成本**：A 做完之後，大約再兩三週處理圖示、啟動畫面、簽章、審查
- **好處**：能上架、能被搜尋到、儲存空間不會被系統清掉、可以接 AdMob
- **代價**：iOS **必須有一台 Mac**（沒有別的辦法）；
  Apple 開發者帳號約每年 US$99、Google Play 約一次性 US$25（以官方公告為準）；
  每次改版都要等審查

### 路線 C — 桌機打包 ✅ 已完成

用 PyInstaller 把現在的程式包成 `.exe` / `.app`，使用者不用裝 Python。

- **狀態**：**可以用了。** `build_desktop.bat` / `build_desktop.sh`，
  產出約 32 MB。設定在 [platforms/desktop/](../platforms/desktop/)
- **好處**：**現在就能讓不會用終端機的人使用**。以推廣來說 CP 值最高
- **代價**：不解決手機
- **還沒做**：圖示、程式碼簽章、安裝檔。清單在
  [platforms/desktop/README.md](../platforms/desktop/README.md)

### 建議順序

```
C（桌機打包）                   ← ✅ 已完成
     ↓  先讓一般人用得到，收真實回饋
A（移植核心到 JS + PWA）        ← 真正的工作量都在這裡
     ↓  同一批人可以直接在手機上用
B（Capacitor 上架）
```

先做 C 的理由：**在投入移植之前，先確認有人真的會用。**
移植是幾個月的事，值得先用幾天的打包換到真實回饋。

**所以現在的下一步不是寫程式，是把桌機版發出去看看反應。**
在有人真的用之前，A 的幾個月投入沒有根據。

## 四、repo 要不要拆

**不要拆。同一個 repo。**

拆成「開源的舊專案 + 閉源的新專案」看起來乾淨，實際上：

- `content/` 那 19 個題組是兩邊都要的。拆了就是**兩份題組**，改一個要改兩次
- 一個人維護兩個會分岔的產品，最後會兩個都做不好
- 使用者的日記格式必須一致，否則匯出檔沒辦法在兩邊互通

**系統隔離是對的直覺，但隔離的單位是資料夾，不是 repo。**
資料夾邊界配上「哪一層可以 import 哪一層」的規矩，就已經是隔離了。

骨架**現在就已經建好了**，手機版開始做的時候只要把東西填進去：

```
content/          共用：題組、版型          ← 誰都可以用
backend/          Python 後端（桌機，用 content）
web/              瀏覽器介面
core/             共用：JS 輸出核心 ← 還沒有，路線 A 的產物
platforms/
  desktop/        PyInstaller 打包（Windows + macOS 共用）
  ios/            Xcode 產生的殼
  android/        Android Studio 產生的殼
```

規矩只有一條：**`platforms/` 底下不寫商業邏輯。**
那些資料夾只放圖示、簽章設定、權限宣告、打包腳本。
所有真正的程式碼都在 `backend/`（桌機）或 `core/`（手機）。

完整的規矩寫在 [platforms/README.md](../platforms/README.md)。

## 五、VSCode、Xcode、Android Studio 混在一起會怎樣

**會很好，這是業界標準做法，不用擔心。**

關鍵在於：**Xcode 和 Android Studio 不是拿來寫程式的，是拿來「出貨」的。**

| 工具 | 開哪個資料夾 | 什麼時候用 |
|---|---|---|
| **VSCode** | 整個 repo | 平常 99% 的時間。寫 `content/`、`backend/`、`web/`、`core/` |
| **Xcode** | 只開 `platforms/ios/` | 設簽章憑證、改圖示、跑模擬器、送審。一週開不到一次 |
| **Android Studio** | 只開 `platforms/android/` | 設簽章、Gradle、跑模擬器、產 `.aab` |

用 Capacitor 或 React Native 的團隊全都是這樣工作的。
沒有人在 Xcode 裡寫共用邏輯——那些檔案根本不在 iOS 專案裡。

三個已知的摩擦，先知道就不會被雷到：

1. **Xcode 的 `.pbxproj` 幾乎沒辦法 merge。**
   如果之後有第二個人一起做，同一時間只能一個人動 iOS 設定。
   用 CocoaPods / SPM 管相依，不要手改那個檔。
2. **兩個 IDE 都會產生一堆機器專屬的垃圾檔**
   （`xcuserdata/`、`local.properties`、`.gradle/`、`DerivedData/`）。
   **`.gitignore` 已經先加好了**，等到真的建資料夾時就不會誤 commit。
3. **iOS 一定要 Mac。** Android Studio 在 Windows 上可以跑，
   所以如果要先試水溫，**先做 Android**。

## 六、授權與「別人拿去賺錢」

專案採 **AGPL-3.0**（見 [LICENSE](../LICENSE)），這個選擇是為了同時滿足兩件事：

**任何人都可以免費使用**——個人、教會、小組、公司內部，永遠免費，不用問。
這是專案的目的，AGPL 完全不擋。

**但別人不能把它閉源拿去賣。** 如果有人改了這份程式碼、換上自己的廣告 ID
拿去上架或架成網路服務，AGPL 要求他**必須連同原始碼一起公開**。
這讓「偷偷拿去變現」在法律上站不住腳，而 MIT 或 Apache 授權則完全允許這件事。

### 那自己上架、放廣告可以嗎？可以

**因為著作權是你的。** 開源授權是你「授權給別人」的條件，不是你自己的義務。
身為唯一著作權人，你可以同時：

- 在 GitHub 上以 AGPL 釋出（別人免費用）
- 自己另外做一個含廣告的版本，用你自己的條款上架 App Store / Google Play

這叫**雙重授權**，MongoDB、Qt、GitLab 都是這樣做的，完全正當。
（AGPL 跟 App Store 條款有已知衝突，但那只限制**別人**拿 AGPL 版本去上架；
你上架的是你自己授權的那份，不受限。）

### 唯一要守住的一件事

**要維持這個彈性，你必須是唯一的著作權人。**

一旦有人送了程式碼 PR 而你直接合併，那段程式碼的著作權是**他的**，
你就不能再把它放進閉源的上架版本了。

[CONTRIBUTING.md](../CONTRIBUTING.md) 已經寫進一條授權條款處理這件事：
送 PR 即表示同意讓維護者以其他條款散布其貢獻。
**這一條要在第一個 PR 進來之前就存在**，事後要一個一個去問，非常痛苦。

> 這份文件是工程說明，不是法律意見。真的要開始收錢之前，值得找律師確認一次。

## 七、推廣的文檔追蹤

以「讓人找得到、看得懂、願意留下」為目標，缺的東西按重要性排：

| | 東西 | 狀態 | 為什麼重要 |
|---|---|---|---|
| 1 | `LICENSE` | ✅ 已加 | **沒有它，別人法律上不能用，也不會有人開 PR** |
| 2 | `CONTRIBUTING.md` | ✅ 已加 | README 一直在邀請開 PR，但沒說怎麼開 |
| 3 | GitHub **About** 欄與 topics | ⬜ 待辦 | 一行描述 + `journal` `diary` `fastapi` `devotional` 等標籤，這是搜尋找得到的唯一途徑 |
| 4 | `CHANGELOG.md` | ⬜ 待辦 | 回頭客靠這個知道有沒有新東西 |
| 5 | Release + 版號標籤 | ⬜ 待辦 | 讓人可以下載某個穩定版，而不是永遠抓 master |
| 6 | Issue 範本 | ⬜ 待辦 | 特別是 bug 回報要問清楚 Python 版本與作業系統 |
| 7 | **英文 README**（`README.en.md`） | ⬜ 待辦 | 目前全中文，等於自己把讀者縮到一小群。GitHub 上英文摘要能大幅擴大觸及 |
| 8 | GitHub Discussions | ⬜ 待辦 | **題組交流的天然場所**——比 Issue 適合分享「我寫了這個題組」 |
| 9 | 自動測試 | ⬜ 待辦 | 見下 |

### 測試是目前最大的缺口

專案目前**一個測試都沒有**，但 README 花了最長的篇幅在講「不會弄丟東西」。
要推廣的話，這兩件事湊在一起是說服力上的弱點——
別人要把自己的日記交給這個程式，而唯一的保證是「相信我」。

最值得先寫的幾個，都在 `storage.py`：

- 存檔讓字數變少時，**一定**會先留一份歷史版本
- 刪除進垃圾桶、救得回來
- `expected_updated_at` 對不上時，第二個分頁存檔會被擋下來
- 換題組時，舊題組的答案不會被清掉
- 匯出再匯入，資料完全一致

不用追求覆蓋率，這五個就夠了。它們正好對應 README 承諾的五件事。

### 一個具體的推廣切入點

題組是這個工具**唯一別人做不出來的東西**——程式好寫，
「問對問題」難寫。所以推廣的主軸應該是題組，不是功能：

- 把 Discussions 開起來，做一個「分享你的題組」的分類
- README 已經在邀稿了，把門檻壓到最低（貼一個 JSON 就好）
- 每收到一個好題組就進 `content/templates/`，貢獻者會自己去講

功能可以被抄，一群人一起累積出來的題組庫不會。
